# 回灌分流（loopback）议题调研与暂缓结论

本文记录 issue #2「Suboptimal way of doing power」的讨论要点与本项目的取舍：
**结论是暂不实现回灌分流**，现有 `2^a·3^b` 分母方案保持不变。

- 议题：https://github.com/djkcyl/D.I.G.E./issues/2
- 状态：讨论充分、工程代价过高，暂缓
- 参与者：Starficz（提出）、Leander / asteraaster / gander03（推导）、djkcyl（上游作者）、Well2333（上游技术负责人）

## 一、问题是什么

当前（以及本仓库现行）的震荡发电方案是「2 分器 / 3 分器拼分母」：一路震荡支路的输入速率只能是母带速率的 `1/D`，其中 `D = 2^a · 3^b`；更细的档位靠「多支路求和」逼近（如 30W + 15W + 3.75W）。

Starficz 指出的两个问题：

1. **精度受限**：任意 `1/x`（x 含质因子 5、7、11…）无法用 2/3 精确表达，只能近似；近似就要多加支路。
2. **能量泄漏（energy leakage）**：支路越多、各支电池到达时刻越不齐，蓄电箱越容易出现「充满后溢出」或「提前烧掉」，多出来的能量被白白浪费。诱发条件被总结为三条：
   - 幅度：求和的分支越多；
   - 相位：对电池实际被烧掉的时刻控制越弱；
   - 缓冲：蓄电箱容量相对单颗电池的能量越小。

他们给出的量化边界：单颗电池能量约 44kJ（高容谷地）/ 64kJ（低容武陵），每多一条支路，最坏会把系统工作区间振幅抬高一档；**只要工作区间能压在 100kJ 以内，就绝对不漏**。

## 二、他们提出的解法

### 1. 回灌（loopback）实现任意 1/x

把分流器的一个输出口接回上游，构造 `1/x = 1/(2^n − l)`（l = 回灌车道数）。

Starficz 证明了这种结构的**周期恒定**：整个系统以 `2^n` 为周期循环，每一次有 1 颗电池进入热能池时，上游恰好收到 `l` 颗回灌 + `2^n − l` 颗新料，输出到热能池的间隔恒为 `(2^n − l) × 4s`，不随相位漂移。

即：**回灌可以让任意分母 x 精确成立，且输出节拍稳定**。

### 2. 二进制编码器 + 末级分流链（gander03）

不回灌也能降泄漏：

1. 先把目标速率放大到 `0.25 < x' < 0.5` 区间（放大 `2^k` 倍）；
2. 用二进制编码器（多分支按 2 的幂求和）逼近 `x'`；
3. 编码器输出再串一段 `1/2^k` 分流链。

泄漏与「编码器分支数」相关，与「末级分流链的深度」无关，所以能把分支数压在上限内（例如 8 支以内），同时靠末级链拿到精度。

gander03 还给了构造例子：`1/997 = (1/2 + 1/2^7 + 1/2^8 + 1/2^9) → 1/512 链`，或 `(1/2^7 + 1/2^13 + 1/2^14 + 1/2^15) → 1/8 链`，两种写法分支数与精度上限互换。

### 3. 质数分流器 / 有理数分流器

Well2333 提到社区已有「任意正有理数分流器」的研究（B 站两篇），本质是用 `2^m·3^n − 1` 这类可分解数去拼 `x/(2^m·3^n − 1)`。争议点在于：<1000 的 168 个质数里只有 19 个能写成 `2^m·3^n − 1`，遇到 1/997 这类需求时前端编码器可能极其复杂。

## 三、上游的回应与结论

1. djkcyl（2026-02-11）：认可这是"solid optimization"，列入研究计划。
2. Well2333（同月）：明确两点顾虑——
   - **离散 tick vs 连续数学**：游戏按 tick 推进，回灌推到极限等于做「二进制/十进制编码器」，是另一类工程；
   - **仿真复杂度与可靠性**：纯 2/3 分流是确定性的、好仿真；回灌要额外验证「回灌不影响输出口频率」和「不产生相位漂移/堵塞」，等于从零设计一套生产线系统。
3. 上游方案是"把回灌当 IC 组件、预验证两个条件"，并称"几天内上线"——**实际没有落地**，仓库在 2026-04-21 之后停更。

## 四、如果要在本仓库实现，需要做什么

1. **组件模型**：新增 `LoopbackComponent`（输入速率 → 输出速率 + 回灌流），与现有 `2^a·3^b` 分支并列。
2. **周期验证**：用 LCM 推导输出周期，再跑逐秒仿真；`MAX_SIMULATION_DURATION = 1200` 的上限要重估（回灌周期 `2^n` 可能远超）。
3. **求解集成**：分支候选池要混入回灌组件；分桶（3×3）与 Pareto 排序需重新校准（回灌方案的"分流器数"语义变了，要按设备占用计）。
4. **蓝图绘制**：`SolutionDiagram` 要能画回灌线（当前只画树状分流）。
5. **分享码**：回灌组件参数（n、l、串联位置）需要新位段。

## 五、评估结论（本仓库暂不做）

- 收益：任意分母、可能减少分支数量与泄漏；
- 代价：内核 + 仿真 + 分桶 + 蓝图四层同时改，且上游技术负责人当年判断"可靠性风险高、仿真成本大"；
- 现阶段的更高优先级：自定义常驻池 / 自定义震荡池（对应 issue #14 / #16 / #13），它们直接解决玩家每天遇到的"算不出/给废解"。

结论：**记录在案，暂不实现**。若后续要做，先按第四节第 1、2 步做离线原型（不接 UI、不进分享码），验证周期与泄漏边界后再谈集成。
