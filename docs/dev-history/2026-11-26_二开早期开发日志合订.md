## 一、05 · 高容武陵电池（6400W / 40s）

- **纯数据接入**：`FactoryDesigner` 只读 `fuel.power` / `fuel.burnTime`，求解内核不改；唯一按燃料 ID 判断的是 `regionLimiter`（谷地不可对武陵电池限速）。
- **硬约束**：分享码按 `FUEL_OPTIONS` 下标编码（5 bit），新燃料**只能追加到 `FUELS` 末尾**，UI 顺序另走 `FUEL_DISPLAY_ORDER`；`selftest-grid-code` 锁定 `customPrimary` 下标仍为 6。
- **改动面**：`constants.ts`、`regionLimiter.ts`（`WULING_BATTERY_FUELS`）、`gridCode.ts`（`WH`）、主/副燃料与常驻行下拉、`public/fuels/wulingHigh.webp`、两个自测、8 语言 changelog。
- **实测**：6600W → 1 台满速、waste 0；5800W → D22.5 = 5689W；单燃料 7300W 只有 2×6400+200 = 13000W 硬顶解——燃料粒度决定的物理限制，不是 bug。

## 三、07 · 自定义常驻池与震荡池口径

最终口径（多次更正后以此为准）：

1. 游戏内按**分钟**计；单台满速 1.5 个/分（40s 燃料）；`W = 燃料功率 × 燃烧时长 ÷ 60 × 个/分`。
2. 震荡池是**一种特殊常驻**：功率从目标缺口中扣除，取分母吸附后的实得瓦数（如 1 个/分中容武陵 → 1/32 → 4000W），不改主/副燃料枚举；「池燃料独占震荡」的早期实现已回滚。
3. 设备按硬件格数计，**48 为整方案（系统震荡 + 池）合计上限**；设备基本不是瓶颈。
4. 传送带每 30 分钟吞 1 个物品 → 口径 B：默认 5% 损耗容忍，分母取 `D ≤ 36`；口径 A（纯设备上限）已废弃。该现象只在开启池时以黄字提示，不作全局约束。
5. `MAX_TARGET_POWER` 32767 → 65535，分享码历史 15 bit 槽保留，超出部分写尾部 `targetPowerWide`（16 bit）；池 / 常驻字段一律尾部可选追加。
6. 震荡池只做单燃料。

黄色池功率线波形：图表内按下标 / 秒数求方波的四次尝试均失败，最终改为与 `powerLog` 共用同一套重采样，后经池零头修复（`poolChartSegments.ts`）与回归测试收口。

## 五、2026-11-27 · 池脉冲电池仿真修复（`a2d940a`）

- 根因：池只按均值抵扣缺口、未进逐秒仿真，电量结果偏乐观（例：目标 5965、1 路 5988.9W、最低 76.8%，游戏内 39 秒耗尽）。
- 修复：`_simulate()` 用原始目标；`_applyPoolSimulation()` 满速带 → 恒定供给、零头 → 脉冲分支（额定功率、周期 2D）；纯常驻 + 池也仿真；`failureDiagnose` 新增场景 C「池零头间歇供电」（`diagPoolBatteryDrain`）。`selftest-osc-scenarios` 场景 2 组成容差 1W → 60W（逐秒整秒对齐误差）。
- 推送：快进 `fork/main` 与 PR #17 分支，无 force push；AGENTS.md 补「拍板后分步执行、汇报精确到包」「命令行一律静默、不弹登录框」两条。
