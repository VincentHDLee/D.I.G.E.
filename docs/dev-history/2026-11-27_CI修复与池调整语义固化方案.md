## 三、现行「冗余阶梯 + 升降档」到底是什么

唯一生产入口：`App.runCalculation` → `factoryDesigner.worker.ts` → `solveWithPoolAdjustChain()`。FactoryDesigner 的 `solve()` 本身只负责普通求解和建盘，不走这条自动调整链。

1. 触发条件：至少一个符合 `isPoolActive` 的自定义池（未禁用、燃料 ID 非 none、投料换成十分位 >0；此函数本身不额外 `resolveFuel`，正常 UI 路径保证燃料有效）；原始候选非空；池电池预检之后候选全部被剔除。初次预检抛错则保持原候选、fail-open，不进链。原始候选为空、保留候选建盘后为 0 也不进链。
2. 基准冗余：`base = max(1200, params.maxWaste)`。FactoryDesigner 同样只在 `params.maxWaste` 为有限数值且大于 1200 时采用它；历史 1000W 或缺省值继续使用 1200W 宽窗。显式大于 1200 的值还参与枚举 / 剪枝，不只是事后过滤。
3. 固定阶梯：只尝试 `MAX_WASTE_RELAX_TIERS_W = [2000, 3000]`，保持已归一化的投料量不变。基准已经大于等于某档就跳过该档，不倒退，也不从用户更大的值缩回 1200W。第一个有解的尝试立即停止，不合并后续步骤的候选。不尝试「同时放宽冗余 + 改变投料」的笛卡尔积，不保证全局最优；单池降到 0 成功便不再升档。
4. 降投料：阶梯尝试完后回到基准冗余，从原值每次 −0.1 个/分直到 0。采用整数十分位步进，避免 `0.1 + 0.2` 一类漂移。目标是第一个 `isPoolActive` 池，其余池不动；降到 0 时将 `maxPerMin = 0` 且 `enabled = false`。没有别的启用池时跳过池预检，有其他启用池时仍预检。
5. 升投料：降档全部无解后，从原值每次 +0.1 个/分；上限取目标池燃料「一台满速投料量」向下落到十分位，同时受全局 1.5 个/分上限约束。例如 40s 电池为 1.5，源矿理论 7.5 也被全局限制在 1.5；自定义慢燃料的实际升档上限可低于 1.5。
6. 页面反馈：冗余放宽和降投料允许用户「套用到参数」，只修改内存参数并标脏，不自动重算；升投料只提示所需实际产出，不提供套用按钮。分享编解码把 `maxWaste` 固定为 1000（套用值不随分享码保留），本地 profile 透传保存。无解诊断按尝试顺序列出类别、冗余、投料及候选前后数；成功路径只显示提示条。
7. 异常、时限与排序：链内求解 / 预检 / 建盘异常退回原结果；预检报告预测缺口，但不替代求解器的逐秒电池校验。全链共用 8 秒预算（App 10 秒超时的 80%），只在尝试之间检查，单次求解不能内部中断。线上建盘仍用 `compareSolutions`；`comparePoolAdjust` 目前只有自测使用。
8. 历史接口边界：`poolBatteryPrecheck.ts` 内的 `solveWithPoolDowngrade` 不是当前生产 worker 入口。它「逐轮选最大功率池、最多 400 次求解」的旧语义不能混写成上述固定阶梯链。
9. 九宫格列只是一段结果分桶：≤100W / 100–500W / >500W；`SEARCH_MAX_WASTE = 1200` 是搜索基准；`[2000,3000]` 是自动重试的绝对上限；三者不是同一概念，不能合并或改分享码位宽。纯常驻 hard-top 与 `poolOverSupply` 另有超限例外。
10. 已知但不在本轮扩展修复的边界：首次 / 单次求解不可内部取消；App 硬超时会丢 trace；`summary.error` 当前回传但 ErrorState 未展示；预检的保守多池估计可能剔除相位错开的可行解。这些问题已列入[待议清单](2026-11-27_池预检调整链边界_待议.md)，不在 CI / 文档任务中顺手重设计。

已有自测已经覆盖固定档位与顺序、跳档、降到 0、升降档上限、首个成功即停、超时、异常、真实建盘标签与排序。本轮把测试接进 CI、补真 FactoryDesigner 边界与输入上限小修、固化文档，不重写求解或调度算法。

1. **风险：把旧断言反成新断言会掩盖真 bug。** 对策是要求独立仿真与现有 `poolPulseRegression.test.ts` 同口径，两条正反场景都验，不只删失败行，不同步修改求解器来迎合旧测试。
2. **风险：Biome 全仓写入造成大 diff。** 只对第五节明确列出的文件执行，最后逐文件审 diff，生产代码不得出现逻辑变化。
3. **风险：新增 CI 测试数量导致执行时间增加。** 当前 5 个 TypeScript 回归合计约 4.1 秒，调整链自测为假回调毫秒级，新增负担很小，不启动服务或安装依赖。
4. **风险：把“阶梯”写成动态功能。** 本方案只固化现有固定档，不设想新的产品公式。未定义的高档扩展只保留待议，不混入本轮。
5. **风险：给 `fromTenths` 截断会改变异常输入显示。** 这是与 FactoryDesigner 已有截断对齐；注意 `isPoolActive` 原始判断保持不变，避免把有效小量输入判无效。正常 0.1～1.5 的枚举序列不得变化。
6. **风险：小修夹带超时、多池等重做。** 明确不做；这些另列待议，必须另行审批。用户需另行指定新阶梯定义时才设计新档扩展。
7. **回滚：** 三个阶段独立提交；CI 问题 `git revert <ci-fix-commit>`，输入边界问题 `git revert <pool-boundary-commit>`，文档问题 `git revert <docs-commit>`。本方案不是数据库、协议或构建产物迁移，不需要额外数据回滚。
