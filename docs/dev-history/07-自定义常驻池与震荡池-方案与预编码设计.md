> **口径更正（2026-11-26 晚，以本节为准）**
> 1. 手动震荡池是**一条特殊的常驻**：只做「预算 → 可覆盖瓦数 / 档位匹配」估算，**不改求解器原有主/副燃料逻辑**（此前"池燃料独占震荡"的实现已回滚）。
> 2. 传送带下线降速（每 30 分钟吞 1 个）**不作全局约束**——普通电池线只要有正瓦数就能维持；只在用户**开启震荡池开关并选定电池**时，用黄字提示「因为下线降速现象影响，手动震荡可能不可靠」。
> 3. 设备口径：每支路 取货口 1 + 存货口（三分器 2 个 / 全二分器 1 个）+ 热能池 1 + 分流器/汇流器各 1（限速器再 +1）。
> 4. 左栏震荡池标题右侧加开关，电池下拉新增「无」。
> 5. 分享码字段继续后置。
> **口径更正 v3（2026-11-26 17:30，以此为准）**
> 1. 设备占用恢复按硬件格数计：取货口 1 + 存货口（三分器 2 个 / 全二分器 1 个，各 1）+ 热能池 1 + **二分器 × 3 + 三分器 × 5** + 汇流器 × 1（限速器 +1）。例：3 个二分器 + 3 个三分器 + 2 存货口 + 1 取货口 + 1 热能池 = 2+1+1+9+15 = **28**。
> 2. 自定义震荡池的功率必须从目标缺口里扣除：求解器按「目标 − 池功率」出方案，结果再把池功率加回展示值，waste 口径不变。
> 3. 池功率取「按分母吸附后的实得瓦数」（如 1 个/分中容武陵 → 1/32 → 4000W，而不是名义 4267W）。
> 4. 左栏标题改为「自定义震荡池」；投料量标签改为「投料量（个/分钟）」。

## 一、目标

1. **自定义常驻池**：用户自己排常驻热能池（燃料 + 台数 + 每分钟投料上限），求解器不再擅自用主燃料 `floor` 补齐；常驻池进分享码，并在方案流程图新增一行展示。
2. **自定义震荡池**：用户选**一种**电池，系统给该电池的「单支最高 / 最低瓦数」区间，用户输入期望瓦数（或投料量，双向回显），在设备容量上限内匹配分母并求解。

## 三、设备容量模型 + 传送带吞物品 bug（震荡池下限来源）

### 3.1 设备容量

实体设备占用（已确认：除特别说明，实体设备都是 1）：

| 元件 | 占用 |
| --- | --- |
| 三分器 | 1 |
| 二分器 | 1 |
| 取货口 I | 1 |
| 存货口 R | 2 |
| 物品准入口限速器 | 1 |
| 热能池 | 1 |
| 汇流器 | 1 |

一路分母 `D = 2^a · 3^b` 的单支成本：`cost(D) = 1 + 2 + 1 + a + b = 4 + a + b`（限速器再 +1）；**48 是整方案合计上限**。新口径下设备几乎不会成为瓶颈（D=36 只占 8，3 路合计 24），真正卡下限的是吞物品损耗。

### 3.2 传送带吞物品 bug

客户端每 **30 分钟**吞掉传送带上 **1 个**物品。速率 `r = 30/D`（个/分）的支路，相对损耗 = `(1/30) / r = D / 900`：

| D | 速率 个/分 | 损耗 |
| --- | --- | --- |
| 24 | 1.25 | 2.7% |
| 36 | 0.83 | 4.0% |
| 45 | 0.67 | 5.0% |
| 72 | 0.42 | 8.0% |
| 288 | 0.10 | 32% |

低速震荡在实战中不可用——这正是现版本会给出 1/288 这类"看着精确、实战被吞"方案的根因。

### 3.3 口径 B 的可运行下限（默认 5% 损耗容忍）

取 `D ≤ 45` 内最大的 `2^a·3^b` = **36**（设备成本 18，远小于 48，**设备不是瓶颈**）：

| 燃料 | 单支最高（满速） | 单支最低（D=36） | 损耗 |
| --- | --- | --- | --- |
| 高容武陵 6400W | 6400W | **3555.6W** | 4.0% |
| 中容武陵 3200W | 3200W | 1777.8W | 4.0% |
| 高容谷地 1100W | 1100W | 611.1W | 4.0% |

结论：高容武陵的单支可用区间是 **3556–6400W**；更细的缺口要靠多支组合或换低一档燃料，不能再靠"把分母拉到几百"。

> 口径 A（纯设备上限，D_max=36864 → 0.17W）已废弃：算得出，实战跑不住。


## 四、模块 A：自定义常驻池

1. 数据：`BasePoolLine { id, fuelId, count, maxPerMin? }`；`CalcParams.manualBaseLines`。
2. 求解：
   - 手动池非空时**只按手动池铺常驻**，自动补齐默认关（`autoPlanBasePools=false` 语义）；
   - 每行校验 `count × 1.5 ≤ maxPerMin`（40s 燃料），超限截断并提示；

3. 分享码：固定 4 行可选尾字段 `hasBaseLines(1) | lineCount(3) | 4×(fuelId 5 | count 4 | maxPerMin 6)` = 64 bit，追加在末尾。

## 五、模块 B：自定义震荡池（单燃料）

### 交互（按你的要求）

```
震荡池燃料： [下拉，8 种燃料]
单支最高瓦数： 6400 W（= 满速 1.5 个/分，常驻）
单支最低瓦数： 22.2 W（口径 B，可运行下限）
期望瓦数 [____] W   ←→   投料量 [____] 个/分   （双向回显）
设备容量上限 [48]（默认 48）
→ 匹配结果：需分母 D=?, 设备占用 cost(D)=?, 是否超预算/是否可达
```

- 输入瓦数 → 自动填投料量（`个/分 = 瓦数 ÷ (燃料功率 × 燃烧时长 / 60)`）；
- 输入投料量 → 自动回填瓦数；
- 输入的瓦数不在 `2^a·3^b` 档位上时，给出**相邻可取档位 + 各自浪费**，由用户挑。

### 求解集成

- `OscBudget { fuelId, targetWatt? , maxPerMin? , deviceLimit }`；
- 分支组合额外过滤：`Σ cost(Dᵢ) ≤ deviceLimit`；
- 结果新增 `budgetUsage { fuelId, matchedWatt, perMin, deviceCost, deviceLimit }`；
- 无解诊断：`目标 - 常驻 > 单支最高 × 支数上限` → 提示"该电池覆盖不到"；`设备超限` → 提示"需要放宽设备上限或换更小分母"。

### 预编码

```ts
// src/utils/oscBudget.ts
export interface OscBudget {
  fuelId: string;
  /** 期望投入（与 maxPerMin 二选一，另一个由换算得出） */
  targetWatt?: number;
  maxPerMin?: number;
  deviceLimit: number; // 默认 48
}
export interface BranchDeviceCost { a: number; b: number; cost: number }
export function deviceCostOf(denominator: number): BranchDeviceCost;
export function maxDenominatorFor(deviceLimit: number): number;      // 穷举 2^a3^b
export function singleBranchRange(fuel: Fuel, deviceLimit: number): { maxW: number; minW: number; minD: number; maxD: number };
export function wattToPerMin(fuel: Fuel, watt: number): number;
export function perMinToWatt(fuel: Fuel, perMin: number): number;
export function matchDenominator(fuel: Fuel, watt: number): { d: number; watt: number; cost: number } | null;
```

## 十二、周期图表「自定义震荡热能池」黄色线波形（2026-11-26 记录，已按重采样对齐修复）

**现象**：池为 1/24、2667W（周期 2D = 48s、燃烧 40s，理论波形是「40s 高位 + 8s 低位」的方波）。
周期图表里的黄色虚线却画成不等宽的凹凸折线；切换「精确数值」后凸起数量变多，明显与理论波形不符。

**已尝试（均未解决）**：
1. 用常量线（`poolPower` 标量）——必然直线，已废弃；
2. 图表内按 `x`（采样点序号）当秒求方波——采样率 ≠ 1s 时相位错位；
3. 求解器输出逐秒 `poolPowerLog`，图表按下标取——采样重排后仍错位；
4. 按 `i × secondsPerPoint` 求值——仍与截图不符。

**怀疑点（下一步排查）**：
1. `secondsPerPoint` 的推导使用 `period / (pointCount - 1)`，而 `powerLog` 实际是按「每秒」生成的，两者在长周期或压缩后不一致；
2. 非精确模式的 4 秒重采样用「就近取点」，会把方波边沿抖动成不等宽；
3. 余量支路可能带准入口限速（`k/5`），实际周期不是 `2D` 而是 `2D·5/k`；
4. 分支相位差（`phaseOffsetBranch`）未参与池波形相位。

**建议的下一步**：让图表与 `powerLog` 共用同一套重采样结果——即求解器额外输出「与 `powerLog` 等长、同重采样」的池功率序列，图表直接用该序列，不要在图表里再算时间；或者直接从 `burnStateLog` 的对应支路反推。

**影响**：只影响图表观感与读数，不影响求解结果、功率扣除与 BOM。

**2026-11-26 夜修复**：
1. 求解器为「纯常驻 + 池」方案合成整周期序列（`_poolCyclePeriod()` 取各池周期 LCM，封顶 600s），同时给出 `poolPowerLog`、`poolLog` 与按秒积分的电池曲线；
2. 图表把 `poolPowerLog` 与 `powerData` 走**同一套重采样与压缩**（4 秒就近取点、超限压缩），不再按下标硬对；
3. 待内测确认波形（每个周期内的高/低段宽度是否与 `2D` 周期一致）。
