## 一、关键结论

1. **「仿真给解但 UI 报无解」在当前代码不存在**：A 组 5965 谷地实测 `solve()` 和 worker 完整链路（`solveWithPoolAdjustChain` + `filterByPoolBattery`）都返回 1 解，`precheck removed = 0`、`allRemoved = false`、`triggered = false`。唯一胜出解：`[valleyHigh D45 lim6, valleyHigh D22.5 lim12]`，`period = 5760 w/ logSecondsPerPoint = 12`，`waste ≈ 1001.67 W`，`minBattery = 10.68%`。`(2000 − 1001.67) × 88 ≈ 87.85 kJ < 95 kJ`，物理站得住。
2. **这是个高浪费解**（≈14% 目标功率），合法但工程上不优。如果你看到 UI 仍报无解，那是**构建版本落后**，不是当前代码 bug。
3. **「池瞬时功率 > 目标 → 池溢出」的独立诊断分支目前不存在**。混合在通用「未找到方案」文案里，用户分不出是「没有可行解」还是「池配置不合理」。这是**唯一遗留工作**，已识别挂载点（poolBatteryPrecheck 与各阶段 chain），留待下次规划。
4. **「熄火期缺口用 remW 当平均值」公式虽写法偏保守，但当前经济和物理误差可接受**，本次不动（避免震荡）。

## 四、未关闭的独立需求

**「池功率溢出」独立诊断分支 + 过载解放行（方案 B）**

- 用户现象：自定义震荡池给 1.5 个以上**高容武陵**（6400 W）时，缺口 4000 W 直接报通用「未找到方案」；给 8 个/分**高容谷地**却能算。
- 真实机制：`FactoryDesigner._applyPoolSimulation` 里 `waste > wasteCap + 0.5` 把「池功率 > 目标 + wasteCap」的纯常驻解**直接 return null** → solve() = 0。诊断层没有专属的「池溢出」分支，被混进通用「未找到方案」。
- 方案 B：**放行这种解**，给它打 `poolOverSupply: { peakW, targetW, overPercent }` 标记，UI 用黄色警告条提示「当前解浪费过大（超出 X%），建议降低投料」。同时**新增** `poolExceedsTarget` 主诊断（只在真无解时用）。
- 挂载点：`FactoryDesigner.ts ≈ L1924-1929`、`failureDiagnose.ts` precheck.allRemoved 之后、`SolutionList` / `DecisionMatrixCard` 摘要区。
- 执行者：core-wire（开发） + 8 语言 i18n。
- **本次接受大浪费解，是为了让玩家看到「这种配置不优但物理可行」**，避免「你说无解，但其实有解只是浪费大」的认知偏差。

## 五、下次子代理规划建议

1. 每次 spawn 只派**有明确写范围的开发任务**，只读分析任务改为一次性 `subagent`（不占名额）。

4. 完整游戏内实测验证：UI 截图需明确**构建 commit**，避免拿旧包测新代码。
