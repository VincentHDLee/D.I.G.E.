## 一、结论先说

新电池是**纯数据接入**，求解内核一行不用改：`FactoryDesigner` 全程只读 `fuel.power` / `fuel.burnTime`，没有按燃料 ID 写死的分支。

真正的坑只有两个：

| # | 坑 | 现状 | 处置 |
|---|---|---|---|
| ① | 分享码/电网码用**燃料在 `FUEL_OPTIONS` 里的下标**编码（`PRIMARY_FUEL_BITS = 5`） | 下标一挪，老分享链接会静默解成别的燃料 | 新燃料**只能追加到 `FUELS` 末尾**，UI 排序另做一层显示序列 |
| ② | 中容/低容武陵电池有 64×64 图标，高容没有 | `public/fuels/` 只有 6 个 webp | 先用中容图生成占位变体，官方素材到位只替换文件、不动代码 |

## 二、证据

**1. 求解器不认燃料 ID**

`src/utils/FactoryDesigner.ts` 全部燃料相关计算只取 `this.primaryFuel.power` / `.burnTime`（L916/L922/L946/L1003/L1027 等）；唯一的燃料 ID 判断在 `regionLimiter`（谷地不可对武陵电池限速）。所以 6400W/40s 一进 `FUELS` 就能算。

**2. 用现有求解器预演 6400W/40s（未改源码，走 `customPrimary` override）**

```
target 5800W →
  1 路 D22.5 = 5689W   waste 88.9   minBatt 72%
  0 路 1台 满速        waste 800    ← 一批电池 + 基地 200W 就够
target 6600W →
  0 路 1台 满速        waste 0      ← 单位功率精确命中
target 7300W（单燃料）→
  0 路 2台 满速 13000W waste 5700   ← 只有硬顶解
target 7300W（+高容谷地副燃料）→
  1 路 D30 = 733W      waste 33.3   minBatt 86%   ← 副燃料补缺口，精细解正常
target 10000W →
  1 路 D33.75 = 3793W  waste 420.9
```

物理事实：1 台满速 6400W，加基地 200W 就是 6600W；目标落在 6600~13000 之间时单燃料必然大浪费，必须靠副燃料或震荡分支补，这是燃料粒度决定的，不是 bug。

**3. 分享码顺序敏感（硬约束）**

`src/utils/shareParams.ts` L264-274：`primaryFuelId` 用 `FUEL_OPTIONS.findIndex` 编码成 5 bit。当前顺序 `ore, valleyLow, valleyMid, valleyHigh, wulingLow, wulingMid, customPrimary`（`customSecondary` 不进主燃料表）。若把 `wulingHigh` 插在 `customPrimary` **之前**，老码里 index 6（自定义主燃料）会被解成高容武陵电池 —— 静默错配，比报错更糟。

**4. 现有基线自测全绿**

```
pnpm exec tsx scripts/_selftest_grid_code.mjs      → all passed
pnpm exec tsx scripts/_selftest_region_limiter.mjs → all checks passed
```

**5. 图标占位样本已生成**（`.snow/icon_variants.png`，从左到右：亮绿增强版 / 青蓝异色版 / 原中容图）

亮绿增强版保留"武陵绿"家族感、亮度更高，读起来就是"同系列更高一档"，推荐用它做占位。
