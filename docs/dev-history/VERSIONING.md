# 开发文档版本与日期标记规则

> 适用：`docs/dev-history/` 的任务书、方案、交付归档与后续设计记录。
> 启用：2026-11-27｜当前交付版本：**v1.12.0.1**（本地验收通过）。

## 一、四位版本按业务变化递增

格式：`v1.12.0.1`。这里管理的是**开发文档与开发轮次**，不直接改软件包、分享码或公告版本。

| 位置 | 当前值 | 递增条件 |
| --- | --- | --- |
| 第一位 | `1` | 历史文档系列号。未获新的明确指令时保持 `1`，不自行升级。 |
| 第二位 | `12` | **业务大版本**。只在游戏更新、需要调整项目游戏口径或核心规则时考虑递增；游戏未更新不因日常迭代递增。 |
| 第三位 | `0` | **功能模块增改**。新增 / 删除 / 明显改变功能模块时递增，如新增燃料、接入新求解模块、改变池功能结构。 |
| 第四位 | `1` | **bug 修复**。修正求解、仿真、回归测试、CI 或已交付行为的错误时递增。 |

递增示例：当前 `1.12.0.1` 是修复轮；下一个功能模块轮为 `1.12.1.0`；第二位若因游戏更新由 `12` 改到 `13`，后两位重新从 `0.0` 起。

## 二、日期与版本各管一件事

1. 新任务主文档以 `YYYY-MM-DD_主题.md` 命名，日期为实际工作日期；文档头统一标记：
   - `文档版本`：四位业务开发版本；
   - `记录日期`：本次工作日期；
   - `状态`：待审批 / 已批准·执行中 / 已验收 / 已废止；
   - `代码基线`：开工 commit，验收后再补交付 commit。
2. 一个开发轮次的任务书、实施说明、UI 或算法补充说明、验收归档共用同一个版本；同轮次的多个本地 commit 不各自递增版本。
3. 下一轮即使仍修 bug，也启用新任务主文档并递增第四位；不覆盖历史任务书来假装新工作从未发生。
4. 重大口径变化同时记录日期、版本和批准状态，历史任务书保留当时结论。若旧结论已被废止，在头部加指向新版本的说明，不大段改写原现场。
5. 文档错字、排版、纯索引更新不单独制造业务版本；若同时承载新的 bug 修复或模块工作，使用该开发轮次的版本登记。
6. 一个任务结束必须把结果摘要、验收命令、提交号、`已验收` 状态写回对应任务文档，并更新 [索引](README.md)。

## 三、历史文档只登记，不反推不存在的版本

1. 2026-11-27 之前的 05～08 号文档，保留原有 v1.11.x 口径；当天已存在的其他文档保留原有 v1.12.x 口径。
2. 历史文件在头部补「记录日期 + 原文版本口径 + 归档登记」，不根据后来功能多少虚构一套历史四位号，也不把当时的包版本冒充游戏版本。
3. [README.md](README.md) 的索引列出每份文档的**记录日期、版本口径、主题和状态**，按日期倒序；四位版本只用于启用本规则后的新工作。
4. 文件名、原始 Git 记录和原有 `v1.11.x` / `v1.12.x` 说法都作为考古证据保留，不因登记而回写历史提交。

## 四、与软件版本、git、决策流程的边界

- `package.json`、应用展示版本、announcement / changelog、原生应用版本不因开发文档登记而自动变化；发布软件版本须另行走发布决策。
- 四位文档版本不是 git tag 声明，也不是分享协议字段；不得改现有协议位宽来承载它。
- 先方案、批准、编码、验证、再提交文档状态的流程不变。任务文档标为「待审批」不等于编码授权。
- 一次开发轮次若同时含 bug 修复和模块增改，按最高变化级登记模块版本；本轮经明确批准只有 CI / 回归 / 边界 bug 修复及文档固化，因此为 **v1.12.0.1**，不为新增说明文档单独递增第三位。
